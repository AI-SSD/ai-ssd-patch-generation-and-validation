## Audit Scope & Method

This document audits the pipeline **as depicted in the methodology diagram**, cross-checked
against the **actual implementation**. Each phase was reviewed in isolation, then a second,
independent reviewer re-opened the cited source files and confirmed or refuted every factual
claim; only the verified text is reproduced here.

**Conventions used below**

- Factual claims are backed by `file:line` citations into `pipeline/`. Claims confirmed against
  the code are marked **VERIFIED**; anything that could not be confirmed is explicitly flagged
  *unverified*.
- **Diagram vs. Code** subsections record where the diagram and the implementation disagree —
  these are the highest-value audit findings and are deliberately *not* smoothed over.
- Two project-wide invariants are treated as audit criteria, per `pipeline/CLAUDE.md`:
  1. **Project-agnostic:** no project-specific logic in Python and **no per-CVE configuration**
     anywhere; everything project-specific lives in the per-project YAML.
  2. **Reproducer source:** the methodology uses **ExploitDB as the primary reproducer** and
     the in-tree regression-test reproducer (`poc_language="intree-test"`, "Option A") as the
     **secondary** one. Option A was re-enabled (2026-06-21) via `reproduction_strategy:
     [exploitdb, intree]` in nearly all shipped project configs; `pipeline/CLAUDE.md` was
     updated to reflect this. Where the diagram still shows ExploitDB-only, this is a
     **diagram lag** — the code and CLAUDE.md now agree that both paths are active.

## Phase 0: CVE Aggregator

### Purpose
- Build the per-project CVE+PoC dataset that every later phase consumes: a `results/*_cve_poc_complete.csv` plus a global and a filtered JSON dataset and standalone PoC files under `exploits/`. The orchestrator declares the chain `CVEFetcher → CommitDiscovery → PoCMapper → DataAggregator → SyntaxValidator → PoCRepairLLM → OutputGenerator` (`cve_aggregator/pipeline.py:30-38`), driven by a shared `context` dict (`pipeline.py:123-142`). VERIFIED.
- The diagram collapses these **seven** modules into **five** boxes. Reconciliation: box 1 "Fetch & Enrich CVEs" = CVEFetcher; box 2 "Discover Commits" = CommitDiscovery; box 3 "Map PoCs to CVEs" = PoCMapper; box 4 "Validate & Repair PoCs" = SyntaxValidator + PoCRepairLLM; box 5 "Build Dataset" = DataAggregator + OutputGenerator. Note the diagram order puts "Build Dataset" last, but DataAggregator actually runs *before* SyntaxValidator/PoCRepairLLM in the code (`pipeline.py:34-37`); only OutputGenerator runs last. So box 5 spans two non-adjacent chain positions.
- The same `DEFAULT_PIPELINE` order drives both the orchestrated run and the standalone Phase-0 entry point (`python -m cve_aggregator` → `cli.py` → `PipelineOrchestrator`, `cve_aggregator/cli.py:32,73,109-111`), so the ordering observations below apply to both.

### Inputs
- NVD 2.0 API by `keywords` and/or `cpe_match` from `cve_fetcher` config (`modules/cve_fetcher.py:39,96-150`); validation requires at least one of the two (`cve_fetcher.py:37-44`). Optional CVE.org enrichment only when `enrich_with_cve_org: true` (`cve_fetcher.py:84-86`) — in glibc this is `false` (`glibc_config.yaml:136`), so the diagram's "CVE.org" source is configured OFF for the default project. The aggregated dataset even self-labels `source_apis: ["NVD"]` (`data_aggregator.py:102`). VERIFIED.
- A local ExploitDB clone (`poc_mapper.exploitdb_path`, resolved against `SSD_PIPELINE_ROOT` via `resolve_input_path`, `modules/base.py:26-46`, `poc_mapper.py:55`); the CVE→exploit map is parsed from `files_exploits.csv`/`files_shellcodes.csv` (`poc_mapper.py:168-197`). VERIFIED.
- A local clone of the project's git repo (`commit_discovery.repo_url`/`repo_local_path`, `commit_discovery.py:62-65`). VERIFIED.
- NVD/OpenAI API keys via env vars or single-line key files (`cve_fetcher.py:100-109`). VERIFIED.

### Process
1. **Fetch & enrich (CVEFetcher).** Pre-flight reachability probe (`cve_fetcher.py:176-211`); a pre-flight failure or a total NVD outage (every configured query failed at the transport level) raises `FatalPipelineError` and halts the run regardless of `abort_on_error` (`cve_fetcher.py:60-78`, fatal handling at `pipeline.py:143-150`). Parses CVSS/CWE/refs/affected-CPE-version-ranges (`cve_fetcher.py:275-350`); de-dups, year-filters, and applies a configurable relevance filter (`cve_fetcher.py:366-470`). VERIFIED.
2. **Discover commits (CommitDiscovery).** Builds an in-memory commit-message index (`commit_discovery.py:79`), finds the fixing commit per CVE (`find_cve_fix_commit`, `commit_discovery.py:184-200`), then derives the **vulnerable parent** as the *git parent of the fix commit* (`get_parent_commit(repo_path, fix)`, `commit_discovery.py:208`). Extracts vulnerable+patched file content and diffs them into changed code units (`commit_discovery.py:245-262`). Runs across CVEs with a `ThreadPoolExecutor` (`commit_discovery.py:138-156`). VERIFIED.
3. **Map PoCs (PoCMapper).** Updates/loads ExploitDB, performs the **reverse-search** to discover ExploitDB-only CVEs not returned by NVD (`poc_mapper.py:79-84,317-408`), then cross-references each CVE and runs a runnability filter that drops prose write-ups / CVE-mismatched entries, retaining verified-but-unrunnable ones as `manual_poc_leads` (`poc_mapper.py:90-157`). VERIFIED.
4. **Validate & repair (SyntaxValidator → PoCRepairLLM).** Per-language syntax checks set `needs_manual_review=True` and copy the PoC plus a `<CVE>_<idx>.validation.json` into `manual_supervision/` (`syntax_validator.py:104,273-278,908-913`); PoCRepairLLM attempts LLM repair, and a successful repair clears the flag at CSV-build time (consumed at `output_generator.py:542`). VERIFIED.
5. **Build dataset (DataAggregator → OutputGenerator).** DataAggregator builds the `Dataset`/`CVEEntry` model and merges any prior on-disk dataset (`data_aggregator.py:32-76,82-104`). OutputGenerator writes global JSON, filtered JSON, the CSV, and PoC files (`output_generator.py:72-104`). VERIFIED.

### Outputs
- Global JSON, filtered JSON, CSV, and `exploits/` PoC files (`output_generator.py:76-99`). The CSV is the contract Phases 1+ depend on. VERIFIED.
- CSV columns (code default `output_generator.py:281-289`; glibc override `glibc_config.yaml:416-441`): `CVE, V_COMMIT, V_COMMIT_TIMESTAMP, V_COMMIT_YEAR, FilePath, F_NAME, UNIT_TYPE, V_FILE, V_FUNCTION, CVE_Description, CWE, CWE_Description, project_version, project_version_normalized, ubuntu_version, poc_index, poc_path, poc_language, FIX_COMMIT, TEST_PATH, TEST_SUBDIR, manual_review_required, manual_verified`. The glibc `csv_fields` override omits `V_COMMIT_TIMESTAMP`/`V_COMMIT_YEAR`, but the code force-reinserts them after position 1 (`output_generator.py:292-295`). VERIFIED.
- Rows are a cross-product of changed-code-units × PoCs (`output_generator.py:799-816`); production-source units are preferred over test-file units (`output_generator.py:711-725`). `manual_verified` is written as `"pending"`/`"done"` mirroring `manual_review_required` (`output_generator.py:812-813`). VERIFIED.
- The `FIX_COMMIT`/`TEST_PATH`/`TEST_SUBDIR` columns are populated only for in-tree-test rows (`output_generator.py:807-811`) — they exist precisely because the dormant-but-active Option-A path emits them (see Risks).

### Dependencies
- Phase 1 reads `csv_path` for `V_FUNCTION`/`F_NAME`/`FilePath`, `poc_path`/`poc_language`, era/version fields, and the manual-review flags. The orchestrator binds `csv_path` via `config.resolve_phase0_outputs()` (`orchestrator.py:34`) and consumes it at `orchestrator.py:177`. VERIFIED.
- Manual Review Gate depends on `manual_review_required`/`manual_verified` columns plus `manual_supervision/` reports and `.ok` markers (`orchestrator.py:500-532,751-790`). VERIFIED.
- External: NVD HTTP (and CVE.org when enabled), ExploitDB git clone, project git clone, optional LLM for repair.

### Risks or Issues
- **[RESOLVED in CLAUDE.md 2026-06-21] Option A now the secondary reproducer.** The `reproduction_strategy: [exploitdb, intree]` knob takes precedence over `harvest_regression_tests: false` (`base.py:66-71`); OutputGenerator emits `poc_language="intree-test"` rows (`output_generator.py:607-651`). `pipeline/CLAUDE.md` was updated to document this explicitly: ExploitDB = primary, intree-test = secondary. **Remaining gap: the methodology-v3.xml diagram still depicts ExploitDB-only** — the diagram should be updated to show both sources. VERIFIED.
- **Reverse-search CVEs never get commit discovery and are dropped (high).** Reverse-search adds new CVE dicts inside PoCMapper (`poc_mapper.py:81-84,365-372`), which runs *after* CommitDiscovery in the chain (`pipeline.py:32-33`). Those late-added CVEs therefore have no `project_state`; DataAggregator sets `has_commits = (fix_commit_hash is not None)` → False (`data_aggregator.py:124-136`), so they fail the `filtered_require_commit` check in `include_entry` (`output_generator.py:212`) and are excluded from the filtered dataset/CSV. (Caveat: a reverse-search CVE that was discovered AND given a fix commit in a *previous* run could survive via the on-disk merge in `data_aggregator._load_existing`/`_merge`, `data_aggregator.py:82-104,145-159`; a genuinely new one is dropped.) The diagram's placement of "ExploitDB reverse-search" inside step 1 (before Discover Commits) is therefore wrong about ordering as well: reverse-search runs in step 3, after commit discovery. VERIFIED.
- **Diagram puts PoC discovery in steps 1 AND 3 (medium).** All ExploitDB mapping (including reverse-search) lives only in PoCMapper = box 3 (`poc_mapper.py`). CVEFetcher contains no ExploitDB code (grep of `cve_fetcher.py` confirms no ExploitDB references). The "(… + ExploitDB reverse-search)" annotation on step 1 is not implemented there. VERIFIED.
- **Project-agnostic principle — minor smell (low).** `output_generator._is_test_file` hardcodes naming heuristics including the glibc-flavoured `tst-`/`tst_`/`bug-` prefixes (`output_generator.py:45-60`). The docstring calls these "project-agnostic naming conventions", but `tst-`/`bug-` are glibc idioms; this is arguably borderline against the "no project-specific logic in Python" rule (CLAUDE.md core principle). No per-CVE configuration was found anywhere in this region, so the stricter "no per-CVE configuration" rule appears upheld. VERIFIED.
- **NVD relevance filter is permissive by default (low).** `_is_target_related` returns `True` as its final fallback (`cve_fetcher.py:470`), and the filter is only applied at all when one of `strong_keywords`/`non_target_indicators`/`strict_target_matching`/`require_project_cpe_match` is configured (`cve_fetcher.py:409-411`); without `strict_target_matching`/`require_project_cpe_match`, unrelated CVEs can enter the funnel. VERIFIED.

## Phase 1: Vulnerability Reproduction

### Purpose
- Confirm each Phase-0 CVE is reproducible by building a known-vulnerable image and running its PoC, capturing a **deterministic baseline** (the PoC's own exit code, or a `-1` timeout sentinel) that Phase 3 later compares the patched build against. The orchestrator is explicit that the container computes no verdict; the host decides reproduction via baseline-exit-code matching plus a negative filter (`orchestrator.py:2329-2346`; the wrapper exits with the PoC's own code at `orchestrator.py:1834-1835`).
- The class `PoCAnalyzer` is reduced to two jobs only: decide *how to run* the PoC and *flag explicit failures* — it "no longer produces positive verification logic" (`poc_analyzer.py:229-235`). Verified: it exposes `validate_poc_static` (`poc_analyzer.py:287`), `analyze_poc` (execution strategy only, `poc_analyzer.py:396`), and `negative_filter` (`poc_analyzer.py:753`).

### Inputs
- Phase 0 dataset CSV `results/*_cve_poc_complete.csv`, parsed by `CSVParser.parse` (`orchestrator.py:762-776`). Matches the diagram's "Phase 0 --(dataset CSV)--> step 1" edge.
- A **Phase-1 readiness gate** during parsing requires BOTH a fixing commit (`V_COMMIT`) and a `poc_path`; rows missing either are skipped before any build (`orchestrator.py:806-813`). The diagram does not show this pre-filter. (CONFIRMED.)
- Per-project Phase-1 settings resolved from the active Phase-0 YAML (`_resolve_phase1_settings`, `orchestrator.py:179-278`): `version_era_map`, `commit_era_map`, `install_prefix`, image layout, build/run/launch scripts, package lists. `config.yaml` supplies global timeouts and Docker limits (`config.yaml:27-53`), the baseline determinism policy (`config.yaml:31-41`), and the shared `llm:` backend used by the negative filter (`config.yaml:87-144`). NOTE: `config.yaml:87-144` is the *shared* `llm:` block (provider, model, timeouts) consumed by all LLM phases — there is no negative-filter-specific config section.

### Process
1. **Resolve Build Era (diagram step 1).** Era resolution is two-tier and runs during CSV parsing, not as a separate runtime step. **Gate B (era-by-version)** is preferred: `resolve_build_ubuntu_version_by_version` reads the checked-out tree's version from `version_file` via `git show <commit>:<file>` + `version_regex` (`get_tree_version`, `orchestrator.py:456-489`), then maps it through `version_era_map` by closest-older match (`map_version_to_era`, `orchestrator.py:492-519`; resolver at `orchestrator.py:522-545`, called at `orchestrator.py:881-884`). It **falls back to the commit-date `commit_era_map`** (`resolve_build_ubuntu_version`, `orchestrator.py:393-453`) only when the version can't be read (`orchestrator.py:885-890`). Implements the diagram's "tree version -> Ubuntu base" and the CLAUDE.md backport-correctness rationale. (CONFIRMED.)
2. **Build Base + CVE Image (diagram step 2).** `BaseImageBuilder.ensure_base_image` builds one base image per Ubuntu version and reuses it across CVEs, keyed by `built_images[ubuntu_version]` plus a recipe/label match for cached images (`orchestrator.py:1130-1228`) — matches "reuse base images per ubuntu_version." Required packages are installed with a hard `apt-get install -y git ca-certificates {required_packages}` (no `|| true`), so a 404 on an EOL mirror aborts the build loudly (`orchestrator.py:1073`; `apt-get update` is retried at `orchestrator.py:1072`); optional packages are best-effort (`orchestrator.py:1076`). The CVE-specific image is derived from the base via `build_cve_image` (invoked at `orchestrator.py:3623-3625`). (CONFIRMED; note the install line is 1073, not 1072.)
3. **Run wrapper (diagram step 3).** The baked wrapper runs the PoC, prints a `SSD_RESULT: ... exit_code=$exit_code` marker, and `exit $exit_code` — propagating the PoC's OWN exit code as the container StatusCode (`orchestrator.py:1820-1835`). A trailing `|| true`/`|| :` is stripped so the signal is not masked (`orchestrator.py:1674`). C PoCs are launched through the project's own loader (`ld.so --library-path`, via `phase1.poc_launch_script`) so the build's libc is exercised; interpreted PoCs deliberately do NOT get the loader/`LD_LIBRARY_PATH` path to avoid the interpreter SIGSEGV-ing under an ABI-mismatched libc (`orchestrator.py:1693`, `orchestrator.py:1789-1795`). (CONFIRMED.)
4. **"PoC links project build?" decision (diagram rhombus 1) = the honesty gate `poc_uses_project_build`.** After building, `read_poc_uses_build` reads a baked `.ssd_poc_uses_build` marker (or runs a live `ld.so --list`/`ldd` check) to record `"yes"`/`"no"` (`orchestrator.py:2512-2555`, called at `orchestrator.py:3683-3685`). On `"no"` the code attempts an **era fallback** (rebuild on the next-older Ubuntu, `orchestrator.py:3691-3717`) and then an **i386 arch fallback** (`_try_i386_rebuild` at `orchestrator.py:3139`, invoked at `orchestrator.py:3722-3727`); if still `"no"` after all three, the CVE is routed to manual revision (`orchestrator.py:3729-3741`). This is the "No -> Manual Revision" path. NOTE: the code's actual fallback chain (era + i386) is richer than the single edge the diagram draws. (CONFIRMED.)
5. **Deterministic baseline capture.** `_capture_baseline` re-runs the PoC up to `baseline_runs` (default 3) times; a marker-present crash/exit is early-accepted once `baseline_min_agree` (default 2) runs share the exact `(exit, marker, timeout)` signature, while a timeout baseline requires **unanimity** across all runs; anything else returns `None` → "Non-deterministic PoC" → manual revision (`orchestrator.py:3274-3324`; routing at `orchestrator.py:3788-3812`; policy in `config.yaml:31-41`). A baseline-memoization cache can skip re-running when an identical image + runtime policy already produced a reproduced baseline (`orchestrator.py:3765-3782`, lookup `orchestrator.py:3219-3246`). (CONFIRMED.)

## Phase 2: Patch Generation

Audit of the green "Phase 2: Patch Generation" swimlane in methodology-v3.xml against `patch_generator.py` and `cve_aggregator/utils/code_parser.py`. Diagram steps: (1) Code Analysis & Prompting (Vuln code + CVE/CWE context + PoC), (2) Generate Patch (LLM inference), (3) Extract Artifacts (patched function + helpers). Input edge from Phase 1 (reproduced + baseline); output edge "patch artifacts" to Phase 3; a feedback edge from Phase 3 (max 3 re-prompts) re-enters step 1.

### Purpose
- Generate a candidate security patch for each reproduced CVE using the configured LLM, then structurally validate it and persist artifacts for Phase 3. The phase docstring states this (`patch_generator.py:2-11`).
- Gate by Phase 1 reproduction: only CVEs with a non-null `baseline_exit_code` in `image_manifest.json` and not flagged `needs_manual_revision` are processed (`patch_generator.py:2137-2148`). This realizes the diagram's "reproduced + baseline" input edge. **Caveat: the gate fails open** — if the manifest can't be parsed the filter is skipped and *all* CVEs proceed (`patch_generator.py:2150-2151`), and a missing manifest likewise proceeds with all CVEs (`patch_generator.py:2152-2153`).
- Phase exits non-zero if zero syntactically valid patches were produced from eligible CVEs (`patch_generator.py:2516-2518`), exits 0 cleanly when no CVE was eligible (`patch_generator.py:2509-2511`), and exits 1 on a hard data/load error (`patch_generator.py:2512-2514`).

### Inputs
- **Phase 0 CSV** (`results/*_cve_poc_complete.csv`; the legacy semicolon `documentation/file-function.csv` is also supported, delimiter auto-detected at `patch_generator.py:1699-1709`). Required columns `CVE, FilePath, F_NAME, V_FILE, V_FUNCTION` (`patch_generator.py:1733-1736`).
- **Per-CVE fields consumed** in `process_single_vulnerability`: `F_NAME`, `V_FUNCTION`, `V_FILE`, `FilePath`, plus optional `CVE_Description`, `CWE`, `CWE_Description` for prompt enrichment (`patch_generator.py:1781-1802`).
- **PoC source**: read from `exploits/<CVE>.<ext>` (the primary, non-`_pocN` variant; first sorted candidate; truncated to 3000 chars) by `_find_poc_source` (`patch_generator.py:230-252`).
- **Phase 1 manifest** (`phase1.image_manifest_path`, resolved in `main()` at `patch_generator.py:2415-2423`) for the reproduction gate.
- **Project `phase2:` YAML section** supplying `language`, `system_prompt`, `feedback_system_prompt`, `internal_headers` (`patch_generator.py:213-227`; glibc C values at `glibc_config.yaml:454-474`, tomcat Java values at `tomcat_config.yaml:315-326`).
- **LLM config** from `config.yaml` `llm:` (provider, model(s), endpoint, temperature, tokens, retries) at `patch_generator.py:47-94`.

### Process
- **Row selection (one-best-per-CVE)**: `load_vulnerability_data` drops rows with empty/NaN `V_FUNCTION`/`F_NAME`/`FilePath` (logging the skipped CVEs), then `drop_duplicates(subset=['CVE'], keep='first')`, relying on Phase 0 ordering rows best-first (`patch_generator.py:1740-1761`). This matches the diagram's per-CVE granularity, but the "best row" guarantee is an **unverified assumption about Phase 0 ordering** (asserted only in a comment, `patch_generator.py:1754-1756`; not validated within Phase 2).
- **Step 1 — Code Analysis & Prompting**: `_build_vulnerability_context` assembles three optional sections — VULNERABILITY DESCRIPTION (from `CVE_Description`, capped 900 chars), WEAKNESS CLASS (`CWE` + `CWE_Description`), and PROOF-OF-CONCEPT EXPLOIT (the PoC source) (`patch_generator.py:255-288`). `create_patch_prompt` embeds the CVE id, function name, that vuln context, the **vulnerable function** (the SEARCH anchor), and the **full file context truncated to 4000 chars** (`patch_generator.py:291-329`). The diagram's "Vuln code + CVE/CWE context + PoC" is faithfully implemented (subject to the PoC-path caveat in Risks).
- **System prompt** = project `system_prompt` preamble + the hardcoded `_SEARCH_REPLACE_FORMAT` edit-format contract (`patch_generator.py:156-174,213-221`). Patches are requested as SEARCH/REPLACE edit blocks, not whole-function rewrites.
- **Step 2 — Generate Patch (LLM inference)**: `call_llm_api` dispatches to Ollama (`_call_ollama_api`, `patch_generator.py:656`) or OpenAI (`_call_openai_api`, `patch_generator.py:743`) per `llm.provider` (`patch_generator.py:870-871`). For OpenAI a single `OPENAI_MODEL` is used regardless of the `llm.models` list (`patch_generator.py:2491-2494`, doc `:846-852`, substitution at `:870`). Retry logic plus an adaptive `max_tokens`/`max_completion_tokens`/temperature fallback for reasoning models (`patch_generator.py:806-831`).
- **[UPDATED 2026-06-25] Ollama model selection is now context-aware, with a Phase-2 family-ramp fallback.** For the provider-profile model ramps, the ollama path (`_call_ollama_api`, `patch_generator.py:736`) reads each model's true context window from the server's `/api/show` (`_model_max_ctx`, `:706`) and **skips any model whose window cannot fit the prompt**, returning `metadata['context_skip']` with a logged reason (`:759-779`); `num_ctx` is capped at `min(NUM_CTX, model_window)` and `num_predict` pinned to the remaining room (`:781`). Phase 2 starts with the first model of the family and, on a context overflow, **advances through the family ramp** (`_generate_with_family_fallback`/`_family_ramp_from`, `:1903`/`:1882`, wired at `process_single_vulnerability` `:1975`) so an attempt-1 patch is still produced — mirroring the feedback loop's skip-and-advance on later attempts. OpenAI is unaffected (it ignores the per-call model and never sets `context_skip`); only a context overflow advances the Phase-2 ramp, other failures stop and defer to the feedback loop. The module's own GPU pre-flight (`wait_for_gpu`, `:643`; distinct from the orchestrator gate at the Cross-Cutting section) was also made **advisory and model-aware** — it no longer aborts the phase when the shared proxy GPU merely has a model resident. VERIFIED (unit-tested + live-verified against the proxy).
- **Step 3 — Extract Artifacts**: `build_patched_file_from_response` (`patch_generator.py:1323-1394`) prefers SEARCH/REPLACE: `parse_search_replace_blocks` (tolerant regex `_SR_BLOCK_RE`, `patch_generator.py:1226-1250`) → `apply_search_replace_blocks` applies each block to the pristine `V_FILE` by exact-then-whitespace-tolerant line match (`_find_block_region`, `patch_generator.py:1263-1320`). Only when **all** blocks apply cleanly is the patch accepted, and the patched function is re-sliced with `_extract_function_text`/`find_function_boundaries` (`patch_generator.py:1349,1397-1403,1093-1169`). If blocks parse but do not all apply, it returns `apply_error` (no whole-function fallback) so the patch is forced invalid (`patch_generator.py:1359-1377,1851-1852`). If no blocks parse at all, it falls back to whole-function extraction (`extract_code_from_response` + `replace_function_in_file`, `patch_generator.py:1379-1394`).
- **Structural validation**: `validate_syntax` runs `validate_function_structure` (brace/paren balance on the analysis view + function-decl presence) and, **for C only**, a `gcc -fsyntax-only` compile of the full file; a missing-project-internal-header fatal error downgrades to structural-only (`patch_generator.py:1443-1598`). Non-C languages skip gcc and use structural validation only (`patch_generator.py:1542-1545`), deferring the real compile to Phase 3.
- **Analysis view**: brace-matching/extraction run on `_build_analysis_view`, which blanks comment interiors and non-first `#if/#else` branches while preserving offsets (`code_parser.py:49-124`), so GNU `foo'` apostrophes and preprocessor-duplicated braces don't corrupt the walk. Return-type lines written above the name (GNU style) are pulled into the span via `_DECL_PREFIX_RE`, and K&R param decls via `_KR_PARAMS_RE` (`patch_generator.py:1129-1162`).

### Outputs
The diagram's "patch artifacts" are concretely a per-CVE/per-model directory `patches/<CVE>/<model_safe>/` containing (`save_patch_artifacts`, `patch_generator.py:1608-1693`):

- **`<stem>_function_only<ext>`** — the patched function text. - **`raw_response.txt`** — the verbatim LLM output (`patch_generator.py:1666-1669`);
- **`response.json`** — metadata: `syntax_valid`, `validation_error`, `output_file`, `function_file`, `original_filepath`, `cve_id`, `function_replaced`, plus token/timing and `patch_mode`/`sr_blocks`/`sr_applied` (`patch_generator.py:1671-1683,1835-1837`).

This satisfies the diagram's "patch artifacts → Phase 3" edge (consumption is Phase 3's concern, not audited here).

### Risks or Issues
- **PoC source path is NOT rebased to the run's base-dir.** `_find_poc_source` reads `BASE_DIR / exploits_dir` where `BASE_DIR` is the script's own directory (`patch_generator.py:33,236`), whereas `main()` rebases `OUTPUT_DIR` to `args.base_dir` (`patch_generator.py:2430`) and the manifest path to `base_dir` (`patch_generator.py:2415-2423`). For a run launched with `--base-dir projects/<name>` (the `run_project.sh` pattern, cf. MEMORY "Phase 0 cwd input-path fix"), the PoC is looked up under the script dir's `exploits/`, not the project's — silently dropping the PoC section from the prompt. The CSV path (`CSV_PATH`) has the same static-`BASE_DIR` origin (`patch_generator.py:97`) but is overridable via `--csv` (`patch_generator.py:2426`); the PoC path has no override. This weakens the diagram's "+ PoC" input for multi-project runs. (Severity: correctness/coverage; not a crash. Whether it bites depends on the launcher's `--base-dir`/cwd, not traced here.)
- **Reproduction gate fails open.** Any exception while reading the manifest is swallowed and the run proceeds with *all* CVEs (`patch_generator.py:2150-2151`); a missing manifest does the same (`patch_generator.py:2152-2153`). So a corrupt/misresolved manifest silently degrades the "reproduced + baseline" input edge into "all CVEs", potentially generating patches Phase 3 cannot validate.
- **Feedback prompt loses CVE/CWE description.** The retry path calls `_build_vulnerability_context(cve_id)` with no description/CWE args (`patch_generator.py:1957`), so retries carry only the PoC source, not the description/weakness class the initial prompt had. The docstring acknowledges this (`patch_generator.py:1954-1956`); re-prompts (the diagram's feedback edge into step 1) are therefore strictly less informed than the first prompt.
- **"Helpers" in the diagram are not extracted.** The `_function_only` artifact and the per-CVE row selection are single-function: one `F_NAME` (`patch_generator.py:1397-1403,1660-1664`). If the real fix touches multiple functions/macros (a known glibc case — cf. MEMORY "CVE-2012-3480 unpatchable root cause"), only the primary function is captured in that artifact. The full patched file does carry all SEARCH/REPLACE edits, but the diagram's "patched function + helpers" overstates the per-unit extraction.
- **Whitespace-tolerant SEARCH matching can mis-anchor.** `_find_block_region` falls back to line-stripped matching (`patch_generator.py:1277-1295`); for C this is argued safe, but it can match a different occurrence than the model intended if a stripped line sequence repeats. There is no uniqueness check on the tolerant path — only the prompt asks for uniqueness (`patch_generator.py:170`). No verification that the applied region is the intended one.
- **`gcc -fsyntax-only` on an isolated file is weak.** The full file is compiled with `-w -Wno-implicit-function-declaration` (`patch_generator.py:1555`) and any missing-header fatal error is treated as pass (`is_missing_header_error`, `patch_generator.py:1410-1440,1571-1579`). Many semantic/type errors are not caught at Phase 2; the real gate is Phase 3's in-container rebuild. A patch can be marked "syntax valid" yet fail to compile in context.
- **Project-agnostic posture mostly holds, with one code-level C bias on the fallback path.** Prompts/language/headers are config-driven (`patch_generator.py:213-227`) and the validator branches on `PATCH_LANGUAGE` (`:1542`). However `extract_code_from_response`'s whole-function fallback hardcodes C-style signature regexes (`func_patterns`, `patch_generator.py:975-983`) and `clean_code` hardcodes C type keywords for its code-start heuristic (`patch_generator.py:1046-1052`). These fire **only** on the no-edit-block fallback path (`patch_generator.py:1379-1394`) and do **not** route to `code_parser`'s Java/C# extractors (`code_parser.py:428-592,622-630`), even though those exist. This is C-specific logic living in Python, contrary to the "no project/language-specific logic in code" principle — confined to the fallback, but a real violation there.

## Phase 3: Patch Validation

### Purpose
- Phase 3 validates an LLM-generated patch by reproducing the *exact* Phase 1 environment with one variable changed (the patch) and asking two questions: (a) does the exploit still work dynamically, and (b) did the patch introduce new static-analysis defects. Implemented in `patch_validator.py` (`ValidationPipeline._validate_patch`, `patch_validator.py:1569`).
- The header docstring states the four-step methodology: derive a patched image FROM the Phase 1 CVE image, re-run the same PoC wrapper and compare exit code against the captured baseline, run SAST host-side, generate reports (`patch_validator.py:5-15`).
- A patch is declared `SUCCESS` only when BOTH the dynamic check (`poc_blocked`) and the SAST gate (`sast_passed`) pass (`patch_validator.py:1825-1829`; the dormant in-tree path enforces the identical gate at `patch_validator.py:1565-1567`).

### Inputs
- Phase 2 patch artifacts, discovered under `patches/<cve>/<model>/` by `PatchDiscovery.discover_patches` (`patch_validator.py:443-482`). The full patched `.c` file is the primary input; a host-`gcc`-flagged `_invalid.c` is accepted as fallback rather than dropped (`patch_validator.py:499-520`). Feedback-loop retry directories (`*_retryN`) are deliberately skipped so a standalone re-run does not re-validate each retry (`patch_validator.py:469-475`).
- The Phase 1 manifest (`results/image_manifest.json`), read by `ImageManifest` (`patch_validator.py:577-611`). Per CVE it supplies the built `tag`, `baseline_exit_code`, `needs_manual_revision`, `needs_privileged`, and `sast_baseline` (`patch_validator.py:1634-1650, 1758`).
- The Phase 0 CSV (`VulnerabilityInfo` per CVE: `FilePath`, `F_NAME`, `poc_language`) parsed by `CSVParser.parse` (`patch_validator.py:391-429`).
- The active project's Phase 0 YAML via `--phase0-config`, which drives BOTH the Phase 1 manifest/layout path AND the SAST tool list (`patch_validator.py:1413-1429, 1440-1452`; layout resolver `patch_validator.py:90-132`).
- Global settings from `config.yaml` (`memory_limit`, `build_timeout`, `run_timeout`) (`patch_validator.py:63-64, 1408-1409`).

### Process
1. **Build Patched Image (incremental FROM Phase 1 image).** `PatchedDockerfileGenerator.generate` emits a Dockerfile `FROM {cve_image_tag}` that COPYs `patched_source.c` over `/build/{source_dir}/{vuln_file_path}`, `touch`es it (to defeat preserved-mtime skip), sets `ENV VULN_FILE`, then runs the project-supplied `phase1.patch_rebuild_script` (`patch_validator.py:625-667, 695-729`). This matches the diagram's "incremental FROM Phase 1 image". The CMD (Phase 1 run wrapper) is inherited (`patch_validator.py:665-666`).
2. **Two build-failure feedback gates.** A Docker build failure → `BUILD_ERROR` with logs stored for feedback (`patch_validator.py:1712-1719`). The rebuild script is deliberately tolerant (exits 0 even when the patch does not compile, `patch_validator.py:656-657`); a non-rebuilt object is detected via the `/tmp/ssd_obj_rebuilt` marker read by `read_build_verification` → also `BUILD_ERROR` (`patch_validator.py:856-884, 1724-1734`). An honesty re-check `poc_uses_build == "no"` → `EXECUTION_ERROR` (non-retryable) (`patch_validator.py:1736-1750`).
3. **Re-run PoC + compare to baseline.** `run_poc` re-runs the inherited wrapper under the same memory limit, security_opt, and `--privileged` (for namespace PoCs) as Phase 1, then applies an evidence-based verdict (`patch_validator.py:916-1142`). See "Diagram vs. Code" — the verdict is NOT a simple "baseline matched?".
4. **SAST (host-side).** `run_sast` delegates to the shared `sast_runner.run_sast_file` on the single patched source file (`patch_validator.py:1202-1215`). `_evaluate_sast` classifies findings against the Phase 1 `sast_baseline` into preexisting/resolved/new and gates ONLY on `new` findings in a `fail_on` class (`patch_validator.py:1513-1549`; `sast_runner.classify` at `sast_runner.py:299-328`; `sast_runner.gate` at `sast_runner.py:331-339`).
5. **Final status + report.** `SUCCESS` iff `poc_blocked and sast_passed` (`patch_validator.py:1825-1829`). Reports written by `ValidationReportGenerator` (`patch_validator.py:1238-1349`), output → Phase 4 (`patch_validator.py:1503`).

### Outputs
- Per-patch `ValidationResult` with status, `poc_blocked`, `baseline_exit_code`, `poc_exit_code`, negative-filter evidence (`nf_failed`/`nf_reason`/`nf_source`/`poc_proof_confidence`), and SAST classification buckets (`patch_validator.py:237-308`).
- Individual JSON per patch (`validation_results/<cve>/<model>_validation.json`, `patch_validator.py:1254-1263`) and a `validation_summary_<ts>.json` (`patch_validator.py:1265-1349`).
- `to_failure_context` feeds the feedback loop: status, exit codes, PoC output, build logs, and crucially only `sast_new` (patch-introduced findings, never pre-existing debt) (`patch_validator.py:310-335`, `sast_new` at `:329`).

### Dependencies
- Phase 1 manifest with a usable baseline: missing entry / `baseline_exit_code is None` / no `tag` / `needs_manual_revision` → `NO_BASELINE` and the CVE is not validated dynamically (`patch_validator.py:1634-1645`). This matches CLAUDE.md's "No Phase 1 Baseline" behavior.
- Docker daemon (`ValidationDockerManager.__init__`, `patch_validator.py:813-819`).
- `poc_analyzer.PoCAnalyzer.negative_filter` — the SAME filter Phase 1 uses, here read for the opposite proof (`patch_validator.py:56, 812, 1029-1031`; defined `poc_analyzer.py:753`).
- Host-installed SAST tools — REQUIRED: the orchestrator preflight aborts the whole run if any configured tool is missing when phases 1 or 3 run (`master_pipeline/orchestrator.py:1329-1339`, using the same `load_sast_config`/`detect_tool` as Phase 3, `:1359-1370`).
- Feedback loop (`master_pipeline/feedback.py`): `max_retries` default 3 (`config.yaml:181`, `master_pipeline/config.py:125`) → 4 total attempts (explicitly documented at `config.yaml:188-190`); environment statuses (`No Phase 1 Baseline`, `Execution Error`, `Patch Not Found`) break the retry cycle (`feedback.py:273-280`).

### Risks or Issues
- **Host-side single-file no-build SAST = weak "clean" signal.** SAST runs on one isolated `.c`/`.java` file with no compile database (`patch_validator.py:135-145, 1202-1215`). cppcheck/clang-tidy without the project's headers/types produce mostly surface-level findings; clang-tidy is configured with `--` to suppress missing-header parse errors (`glibc_config.yaml:549`). A "SAST clean" verdict therefore certifies little about a deep memory-safety fix — a false sense of safety, and a likely source of `SUCCESS` for patches that are dynamically-blocked but subtly wrong.
- **semgrep/pmd need network at scan time** (`--config=p/c`, `--config=p/java` rulesets are downloaded; `glibc_config.yaml:557-560`, `tomcat_config.yaml:354`). An offline VM would yield zero semgrep findings silently — `run_tool` marks the tool `success=True` on empty output, so a network failure that does not error the process is indistinguishable from "clean" (`sast_runner.py:241-256`).
- **The dynamic verdict is intentionally asymmetric / strict, which the diagram does not convey.** A different exit code is NOT sufficient: a patched run that still crashes with a signal (`exit >= 128`) or is OOM-killed (137) is rejected even if the code differs from baseline (`patch_validator.py:1040-1042, 1092-1101, 1118-1124`). Defensible methodology, but it means the simple diagram rhombus materially understates the logic.
- **`nf.failed` can flip a SAME-exit-code run to "blocked."** If the negative filter (LLM or regex) reports the exploit failed, the verdict is "blocked [confirmed]" BEFORE the `poc_exit_code == baseline` check (`patch_validator.py:1104-1114`). An LLM misread of PoC stdout could thus declare a still-vulnerable patch fixed. The filter is the same one Phase 1 uses, so the risk is symmetric, but it puts an LLM in the verdict path.
- **Test-file patch guard is project-agnostic but heuristic.** `_load_patch_info` rejects patches whose target basename starts with `tst-/test-/test_/bug-` or lives in a test dir (`patch_validator.py:541-552`). Reasonable, but a vulnerable file legitimately named e.g. `test_*` would be wrongly skipped (edge case, not per-CVE config).
- **No `patch_rebuild_script` → stub fails loudly** (`patch_validator.py:715-728`); good (avoids validating against the old binary), but means a project YAML missing that key produces `BUILD_ERROR` for every CVE.
- **Single-source-file COPY assumes the patch is exactly one file** named `patched_source.c` regardless of real extension (`patch_validator.py:642, 1707-1708`); multi-file fixes cannot be expressed. Consistent with Phase 0/2's single-`FilePath` model — a structural ceiling, not a bug.

## Phase 4: Reporting

### Purpose
- Phase 4 is the terminal "Document Results" step. It is a thin, read-only aggregation pass that ingests the JSON artifacts produced by Phases 1-3 (and the feedback loop), computes aggregate statistics, renders Matplotlib charts, and emits a single timestamped Markdown report. It performs no Docker, LLM, or git work and produces no data consumed by later phases. (Verified by reading `reporter.py` end-to-end — it only reads JSON, calls Matplotlib, and writes Markdown/PNG.)
- Implemented as a standalone script `reporter.py` (`PipelineReporter.generate_report`, `reporter.py:1437-1545`), invoked by the orchestrator as phase 4 (`master_pipeline/config.py:143` maps `4: "reporter.py"`; `master_pipeline/executor.py:32` names it "Automated Reporting").

### Inputs

- **Phase 1**: `results/results.json`, key `results[]` (`reporter.py:249-272`). Producer confirmed: `orchestrator.py:2698` writes `self.results_dir / "results.json"`.
- **Phase 2**: `patches/pipeline_summary.json`, keys `metadata`/`summary`/`results[]` (`reporter.py:283-318`). Producer confirmed: `patch_generator.py:2170,2315` write `pipeline_summary.json`. - **Phase 3**: the most-recent `validation_results/validation_summary_*.json` chosen by mtime via `max(..., key=lambda p: p.stat().st_mtime)` (`reporter.py:330-337`), keys `metadata`/`summary`/`phase_timing`/`by_cve` (`reporter.py:343-391`). ### Process
1. Load Phase 1/2/3 + feedback data (`reporter.py:1442-1457`).
2. 5. Render the Markdown report (`ReportGenerator.generate_full_report`, `reporter.py:952-1049`) with sections: Executive Summary, Pipeline Overview chart, Phase 1/2/3 tables, Model Performance, SAST (incl. baseline-delta at `reporter.py:1226-1230`), CVE-Specific, optional Feedback Loop, Recommendations, and a detailed Appendix.

### Outputs / Metrics — and where they can mislead
- **Reproduction rate** `reproduced/total_cves` where `reproduced = sum(... vulnerability_reproduced)` over Phase 1 results and `total_cves = len(cve_stats)` (`reporter.py:1063-1072`). `cve_stats` is seeded from Phase 1 results, then **also** from any CVE appearing in Phase 2 or 3 (`get_cve_stats`, `reporter.py:562-580`). The denominator is therefore "CVEs that reached at least one of phases 1-3", NOT the full Phase 0 CVE set. CVEs dropped pre-LLM in Phase 2 (empty `V_FUNCTION`/`F_NAME`/`FilePath`) never enter `cve_stats` and silently vanish from every denominator — the report cannot show how many candidates were discarded before generation.
- **Syntax-valid rate** `syntax_valid/total_tasks` from Phase 2 metadata (`reporter.py:1073-1074`). `total_tasks` counts only CVEs that survived to generation, so this overstates coverage relative to the original CVE universe.
- **"Successful Vulnerability Fixes"** = sum of `successful_fixes`, where a fix requires BOTH `poc_blocked` AND `sast_passed` (`get_cve_stats`, `reporter.py:582-583`; summed at `reporter.py:1067`). This is a defensible strict definition, but a CVE with **No Phase 1 Baseline** (per CLAUDE.md, common for non-ExploitDB-reproducible projects) produces zero Phase 3 rows, so it counts as "not fixed" with no distinction between "tried and failed" vs "never validatable". The pie chart (`reporter.py:796-807`) buckets all such CVEs as "Not Fixed", which overstates failure.
- **Pipeline-overview success rates** use independent denominators per phase (`p1_total=len(phase1_results)`, `p2_total=phase2_metadata['total_tasks']`, `p3_total=phase3_metadata['total_validations']`; `reporter.py:883-896`), so the three bars are not on a common base and a casual reader may misread them as a funnel.
- **"Best Performing Model"** = `max(poc_blocked/total_patches)` over `model_stats` (`reporter.py:1078-1081`); with a single configured model (the OpenAI default per CLAUDE.md) this is trivially that one model and the comparison charts collapse to one bar.
- **Avg execution time** averages Phase 3 per-row `execution_time_seconds` (`get_model_stats`, `reporter.py:548-553`), which includes incremental rebuild time, not isolated LLM time. The execution-time chart is even labelled "Average Validation Time per Model" (`reporter.py:851`), which is more honest than "LLM time".

## Cross-Cutting: Orchestration, Manual Gates & Feedback Loop

### Purpose
- This region is the glue the diagram labels "the phases are stitched by an orchestrator (master_pipeline/)". Its job is to (a) sequence phases 0→1→2→3→4, (b) gate the run on the manual-review points the diagram shows, and (c) drive the dashed-red Phase 3→Phase 2 feedback loop.
- Concretely it is implemented by `master_pipeline/`: argument parsing/config build (`cli.py`), the run loop (`MasterPipeline.run`, `orchestrator.py:36`), per-phase subprocess invocation (`PhaseExecutor.execute_phase`, `executor.py:25`), and the retry engine (`IterativeFeedbackLoop`, `feedback.py:9`).

### Inputs
- CLI flags parsed in `parse_arguments` (`cli.py:14`): `--phases` (default `[0,1,2,3,4]`, choices `0..4`, `cli.py:71-78`), `--cve`/`--cves` (`cli.py:54-61`), `--dry-run` (`cli.py:131-135`), `--no-feedback-loop` (`cli.py:144-148`), `--max-retries` (default `MAX_RETRIES`, `cli.py:150-155`), `--project` / `--phase0-config` (`cli.py:80-95`, resolved `cli.py:187-204`), `--auto-skip-manual` (`cli.py:172-179`), `--manual-verify-timeout` / `--manual-verify-poll` (`cli.py:158-170`).
- `config.yaml` (loaded once, cached, `config.py:54-62`): `feedback_loop.{enabled,max_retries,timeout,models_by_attempt,retry_on}` (`config.py:124-126`, `config.yaml` feedback_loop block), `manual_verification.{timeout,poll_interval,auto_skip}` (`config.py:129-135`, `config.yaml` manual_verification block), `phase0_config` pointer (`config.py:176`).
- The active project YAML (`cve_aggregator/<project>_config.yaml`), threaded per-phase via `--phase0-config` and read for `phase1.image_manifest_path`, `phase2`, `sast`, and output paths.
- Phase 0's CSV and Phase 1's image manifest are the data hand-offs that dependency checks gate on (`_check_phase_dependencies`, `orchestrator.py:1478`).

### Process
- **Sequencing.** `run()` iterates `sorted(self.config.phases)` (`orchestrator.py:59`), so execution is strictly ascending and faithful to the diagram's 0→1→2→3→4. (Note: `cli.py:221` already sorts `phases` before building the config, so the loop sort is redundant but harmless.) There is no DAG; it is a linear loop. A non-zero phase result sets `success=False` and every later phase >0 is marked `SKIPPED` (`orchestrator.py:63-71`). Phase 0 is exempt from that short-circuit (`phase > 0` guard, `orchestrator.py:63`).
- **Phase invocation = subprocess, not import.** `execute_phase` builds an argv and runs `subprocess.run(..., cwd=base_dir, capture_output=True, timeout=...)` (`executor.py:85-92`). Phase 0 is `python -m cve_aggregator --config <p0>` (`executor.py:152,160-162`); phases 1–4 are `python <script>.py ...` (`executor.py:154`). The executor also injects `PYTHONPATH`/`SSD_PIPELINE_ROOT` so `-m cve_aggregator` and relative input clones resolve from the pipeline root even when `cwd=base_dir` (`executor.py:73-83`). The feedback loop is the lone exception: it imports `patch_generator.py`/`patch_validator.py` as modules via `importlib` from `BASE_DIR` (`feedback.py:56-79`), so Phase 2/3 logic runs *in-process* during retries, not as subprocesses.
- **Manual gate #1 (Phase 0 "Manual Review Gate").** After a successful Phase 0, `_wait_for_manual_verification` runs (`orchestrator.py:124-129`). It reads the Phase 0 CSV, honors `.ok` marker files (`_check_marker_files`, `orchestrator.py:750`), and computes pending CVEs as those whose *every* PoC needs review and that have no runnable PoC (`_get_pending_manual_cves`, `orchestrator.py:500-532`). Excluded CVEs are stored in `self.skipped_cves` and handed to the executor (`orchestrator.py:128`), which passes them to Phase 1 as `--skip-cves` (`executor.py:184-187`).
- **[UPDATED 2026-06-25] Gate #1 gained a non-interactive (dashboard) poll mode.** The `input()`/`select.select` menu only runs on a TTY; when stdin is **not** a TTY (dashboard / piped runs) and `auto_skip` is off, the gate now enters a **non-interactive poll** (`_poll_manual_gate`, `orchestrator.py:897`) that watches `manual_supervision/` for dashboard marker decisions — `<CVE>.ok` (approve), `<CVE>.skip` (exclude; `_consume_skip_markers` `:878`), `.phase0_proceed` (continue) — and auto-skips the rest after `timeout` (this also fixes a prior EOF busy-loop on `/dev/null` stdin). Per-phase settings are transported by env so `config.yaml` is untouched per run: `MANUAL_VERIFY_AUTO_SKIP`, `PHASE1_MANUAL_GATE` (`config.py:233,237`; `_env_bool` `:211`). The shipped default (`auto_skip: true`) still short-circuits, so default behavior is unchanged. VERIFIED.
- **Manual gate #2 (Phase 1 "Manual Revision").** This is NOT in the orchestration glue. The diagram's "PoC links project build? = No" / "Failure detected? = Yes" routing is implemented *inside Phase 1* (the Phase-1 script `orchestrator.py` at the pipeline root — a different file from `master_pipeline/orchestrator.py` — writes a `manual_supervision/<CVE>.phase1-review.txt` marker and sets `needs_manual_revision`, per pipeline/CLAUDE.md). With the shipped default OFF the description above still holds — flagged CVEs surface only as a missing baseline — so this is strictly opt-in and does not change default behavior. VERIFIED.
- **Feedback loop.** After Phase 3, if `enable_feedback_loop`, `_run_feedback_loop` runs (`orchestrator.py:131-133`). On SUCCESS it promotes the patch and returns (`feedback.py:241-261`); environment statuses ("No Phase 1 Baseline", "Execution Error", "Patch Not Found") break the loop early (`feedback.py:273-280`); exhausting retries marks `UNPATCHABLE` (`feedback.py:282-296`).

## Cross-Phase Synthesis

> Placed after all phase reviews, per audit discipline (no whole-pipeline summary before every phase is examined).

### Executive Summary

**What it is.** This is a five-phase, project-agnostic LLM patch-generation-and-validation pipeline (`/Users/tiagoalmeida/Documents/Tese/ai-ssd-patch-generation-and-validation/pipeline`). Phase 0 (`cve_aggregator/`) curates a per-project CVE+PoC dataset CSV from NVD + ExploitDB + the project git repo. Phase 1 (`orchestrator.py`) reproduces each CVE in a known-vulnerable Docker image and records a deterministic baseline in `results/image_manifest.json`. Phase 2 (`patch_generator.py`) prompts an LLM for a SEARCH/REPLACE patch and emits artifacts under `patches/<CVE>/<model>/`. Phase 3 (`patch_validator.py`) rebuilds the patched image FROM the Phase-1 image, re-runs the same PoC, runs host-side SAST, and emits a verdict. Phase 4 (`reporter.py`) aggregates the JSON summaries into a Markdown report. The whole thing is stitched by `master_pipeline/` (subprocess sequencing, a Phase-0 manual-review gate, and a dashed Phase-3→Phase-2 feedback loop run in-process).

**Overall audit conclusion.** The implementation is materially MORE sophisticated than the diagram (strict asymmetric verdicts, multi-run determinism guards, era+i386 build fallbacks, honesty gates, negative filters) but also DIVERGES from the stated thesis methodology in two load-bearing ways. (1) The single most material finding spans Phases 0/1/3: the diagram and `pipeline/CLAUDE.md` claim ExploitDB is the ONLY reproducer and that the in-tree-test path ("Option A") is dormant — but nearly every shipped config sets `reproduction_strategy: [exploitdb, intree]`, which the code makes SUPERSEDE the legacy `harvest_regression_tests: false` flag (`base.py:66-71`), so the dormant claim is FALSE as-shipped and the live intree path is reachable in Phases 0/1/3. (2) The "Manual Review Gate pauses up to 30 min" is dead config — the timeout is loaded and logged but never consumed; the real gate is a bare `input()` with no deadline, and the shipped default `auto_skip: true` silently excludes pending CVEs rather than pausing. Beyond these, several silent fail-open / fail-quiet seams (Phase 2 manifest gate fails open; Phase 4 swallows chart failures and reports exit 0; reporter never embeds the diffs/rationale the diagram promises) mean the pipeline can produce green-looking results from degraded inputs. The data contract between phases is otherwise consistent. Maturity is research-grade: correct on the happy path, honest in its dynamic verdicts, but with documentation/diagram drift and several "degrade-to-zero-instead-of-erroring" hazards that an unattended run will not surface.

### Cross-Phase Data Flow

The end-to-end data contract was traced against code and is **structurally consistent**, with a few flagged seams.

**Phase 0 CSV → Phase 1.** Phase 0 writes `results/*_cve_poc_complete.csv` (`output_generator.py:281-289`). Phase 1 reads it via `CSVParser.parse` and gates on BOTH `V_COMMIT` and `poc_path` being present (`orchestrator.py:806-813`). CONSISTENT. Note Phase 0's reverse-search CVEs are dropped pre-CSV (no commit discovery), so they never reach Phase 1 — a Phase-0-internal loss, not a hand-off break.

**Phase 1 manifest → Phase 2 / Phase 3.** VERIFIED CONSISTENT. Phase 1 writes `cve_images[]` entries with `cve, tag, baseline_exit_code, needs_manual_revision, sast_baseline, needs_privileged, build_arch, baseline_cache_key` (`orchestrator.py:2238-2266`). Phase 2 reads `manifest.get("cve_images", [])`, keeping CVEs with `baseline_exit_code is not None and not needs_manual_revision` (`patch_generator.py:2137-2148`). Phase 3 indexes the SAME `cve_images[]` array by uppercased `cve` and requires `baseline_exit_code`, `tag`, and not `needs_manual_revision` (`patch_validator.py:599,611,1634-1645`). The key names, the gate predicate, and the `sast_baseline` carry-through all match. **One latent mismatch:** Phase 3 normalizes CVE case (`.upper()`) everywhere (`patch_validator.py:458,599,611`); Phase 2's manifest filter compares raw `e["cve"]` against raw `df['CVE']` with no normalization (`patch_generator.py:2137-2148`) — harmless while Phase 0 emits canonical-uppercase CVE IDs, but a fragile asymmetry. **Fail-open seam:** Phase 2's gate degrades to "process ALL CVEs" on any manifest parse error or a missing manifest (`patch_generator.py:2150-2153`), so a misresolved manifest path turns the "reproduced + baseline" edge into "everything", producing patches Phase 3 then can't validate (NO_BASELINE).

**Phase 2 artifacts → Phase 3.** CONSISTENT. Phase 2 writes `patches/<CVE>/<model>/` with the full patched file, `<stem>_function_only<ext>`, `raw_response.txt`, and `response.json` (`patch_generator.py:1608-1693`). Phase 3 discovers `patches/<cve>/<model>/`, takes the full patched file as primary (accepting `_invalid` as fallback), and skips `*_retryN` dirs (`patch_validator.py:443-520`). The `_function_only` artifact is NOT consumed by Phase 3 (it COPYs the whole file), so the "single function vs helpers" overstatement in Phase 2 does not corrupt Phase 3 — Phase 3 carries all SEARCH/REPLACE edits in the full file. **Structural ceiling propagated end-to-end:** the single-`FilePath` / single-`F_NAME` model in Phase 0 → Phase 2 → Phase 3's single `patched_source.c` COPY means a genuinely multi-file/multi-function fix cannot be expressed anywhere in the chain (consistent, but a shared limitation).

**Phase 3 verdict → Phase 4.** CONSISTENT BUT LOSSY. Phase 3 writes `validation_results/validation_summary_<ts>.json` (`patch_validator.py:1268`). Phase 4 picks the newest by mtime (`reporter.py:330-337`) and reads `metadata/summary/by_cve/sast_counts`. **Two flagged issues:** (a) mtime selection has no run-id/project filter, so a `validation_results/` accumulating files across projects/runs can feed Phase 4 a stale or wrong-project summary; (b) Phase 4 reads ONLY the downstream summaries — it never reads `image_manifest.json` (grep-confirmed) and never reads `response.json` (grep-confirmed). The diagram's "Document Results (diffs, rationale)" is therefore unmet: the report has metrics but no patch diffs and no LLM rationale, because the artifact that holds them (`response.json`) is never opened.

**Feedback loop (Phase 3 → Phase 2).** The dashed edge is real but runs Phases 2/3 IN-PROCESS via importlib (`feedback.py:56-79`), unlike the subprocess model used for the forward path (`executor.py:85`). `to_failure_context()` passes only `sast_new` (patch-introduced findings) plus exit codes/PoC output/build logs (`patch_validator.py:310-335`). The retry re-prompt drops the CVE/CWE description that the initial prompt had (`patch_generator.py:1957`), so the feedback contract is strictly less informed than the initial contract.

**Net:** no broken hand-off in the JSON field contract; the real cross-phase hazards are (1) fail-open/fail-quiet gates that silently change the effective input set (Phase 2 manifest, Phase 4 charts), (2) the intree/ExploitDB methodology drift that is invisible to Phases 2-4 (they gate purely on `baseline_exit_code`, so they cannot tell which reproducer produced it), and (3) the diagram's "diffs/rationale" output that the data contract simply does not carry into Phase 4.
